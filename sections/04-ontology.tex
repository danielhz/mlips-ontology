\section{The MLIPs Ontology}
\label{sec:ontology}
%% ====================================================================

The \MLIPsOntology{} is an OWL\,2~DL ontology organized into three modules
that address the competency questions identified in
Section~\ref{sec:requirements}. We first introduce the ontology through a
concrete example (Section~\ref{sec:running-example}), then describe each
module formally (Sections~\ref{sec:algorithm-module}--\ref{sec:benchmark-module}).
Figure~\ref{fig:ontology-overview} provides an overview. The ontology
includes 27 formal OWL axioms (12 existential restrictions, 6 cardinality
constraints, 5 inverse existence axioms, 2 property chains, and 2 domain
axioms) that enforce data completeness and consistency; the full axiom
catalog with examples is published alongside the ontology at
\url{\mlipsns}. The ontology uses the namespace \texttt{\mlipsns} (prefix
\mlipsprefix{}); Table~\ref{tab:prefixes} lists the external prefixes used.
In the following, we omit the \mlipsprefix{} prefix for concepts and
properties of the \MLIPsOntology{}.

\subsection{Method Module}
\label{sec:algorithm-module}

The Method module models MLIP methods and their hyperparameter
spaces, addressing CQ1, CQ2, CQ8, and CQ9.

\paragraph{Core classes.}
The central concept is $\MLIPMethodC$, representing a specific
MLIP method (e.g., MACE, ACE, HDNNP)---the named recipe for turning
an atomic configuration into an energy, not a trained model. An MLIP
method bundles three components: a parametrised functional form
($\FunctionalFormC$) that maps configurations to energies; a loss
function ($\LossFunctionC$) whose minimisation fixes those
parameters; and a training algorithm used to perform the minimisation
(an $\mlsAlgorithmC$, e.g., Adam, L-BFGS). The first two are
MLIP-specific and live inside the MLIPs ontology; the third is
delegated to ML-Schema through the $\hasTrainingAlgorithmR$ role,
which is the sole alignment point between the two vocabularies. A
key further feature of an MLIP method is its \emph{atomic environment
descriptor}: the mathematical function that maps a local neighborhood
(neighbor positions and types) to an invariant or equivariant feature
vector. Different methods use different descriptors---moment tensors
(MTP), SOAP (GAP), symmetry functions (HDNNP), equivariant message
passing (MACE, NequIP), atomic cluster expansion (ACE)---captured by
the $\hasDescriptorR$ role linking $\MLIPMethodC$ to instances of
$\AtomicEnvironmentDescriptorC$. Each method declares the
$\HyperparameterC$ instances it accepts (cutoff radius, number of
layers, learning rate, etc.), with their names, data types, ranges,
and default values. An $\MLIPRunC$ represents a concrete fitting
activity: it $\appliesMethodR$ an $\MLIPMethodC$, takes a
$\TrainingDatasetC$ as input ($\runsOnR$), and $\producesR$ a
$\TrainedModelC$---the learned parameters (weights) that can be used
for prediction. An $\ImplementationC$ captures a software realisation
of a method in a specific $\LibraryC$ and version. Finally,
$\SimulationTypeC$ represents the kinds of atomistic simulation a
method supports (molecular dynamics, Monte Carlo, geometry
optimisation, phonon calculations, thermodynamic integration).

\paragraph{Core properties.}
The role $\hasHyperparameterR$ links a method to the hyperparameters
it accepts, while $\hasImplementationR$ links it to its software
implementations and $\supportsSimulationR$ to supported simulation
types. The three component roles $\hasFunctionalFormR$,
$\hasLossFunctionR$, and $\hasTrainingAlgorithmR$ link a method to
its functional form, loss function, and training algorithm
respectively. An $\MLIPRunC$ is connected to its method via
$\appliesMethodR$, to its input data via $\runsOnR$, and to the
resulting model via $\producesR$; an optional $\hasTrainingRunR$
links an $\MLIPRunC$ to an underlying $\mlsRunC$ when the training
algorithm is itself modelled in ML-Schema. For convenience, a
$\TrainedModelC$ also carries the shortcut roles $\trainedWithR$ and
$\trainedOnR$ (derivable as property chains through the run),
enabling direct queries without navigating the run entity.
Domain-specific datatype properties---$\cutoffRadiusR$, $\numLayersR$,
$\learningRateR$, $\numRadialBasisR$, and $\numAngularBasisR$---record
concrete hyperparameter values, with units annotated via
QUDT~\cite{hodgson2014qudt}. The role $\implementedInR$ connects an
implementation to its library. Efficiency metadata is split along two
dimensions. Prior knowledge about a method---its asymptotic complexity
and whether it supports GPU or parallel execution---is recorded on
$\MLIPMethodC$ via $\dlRole{trainingComplexity}$,
$\dlRole{inferenceComplexity}$, $\dlRole{supportsGPU}$, and
$\dlRole{supportsParallelization}$. Measured training cost
(wall-clock time, hardware, peak memory, GPU hours) is recorded on
$\MLIPRunC$, while measured inference cost is recorded on the
corresponding $\BenchmarkResultC$ (see Benchmark Module).

\paragraph{Axioms.}
The Method module defines axioms that capture the component structure
of an MLIP method: existential restrictions require every method to
declare at least one hyperparameter, at least one simulation type, a
functional form, a loss function, and a training algorithm.
Cardinality constraints ensure each $\MLIPRunC$ applies exactly one
method, uses one dataset, and produces one model. Domain axioms
restrict $\hasHyperparameterR$, $\hasImplementationR$, and
$\supportsSimulationR$ to $\MLIPMethodC$. An explicit disjointness
axiom states $\MLIPMethodC \sqcap \mlsAlgorithmC \sqsubseteq \bot$.
Notably, the shortcut roles on $\TrainedModelC$ are defined as
property chains through the MLIP run:
%
\begin{align*}
  \trainedWithR &\equiv \producesR^{-} \circ \appliesMethodR \\
  \trainedOnR &\equiv \producesR^{-} \circ \runsOnR
\end{align*}
%
These allow direct queries (``which method produced this model?'')
without navigating through the $\MLIPRunC$ entity.



\subsection{Training Data Module}
\label{sec:training-data-module}

The Training Data module describes the datasets used to train MLIP models,
addressing CQ3, CQ4, and CQ5.

\paragraph{Core classes.}
A $\TrainingDatasetC$ is a collection of atomic configurations used for MLIP
training. Each dataset covers one or more $\MaterialSystemC$ instances
(elements, alloys, compounds), and its reference data is produced by one or
more $\ReferenceCalculationC$ instances. The two concrete subclasses are
$\DFTCalculationC$ (governed by $\DFTSettingsC$ with the
exchange-correlation functional ($\xcFunctionalR$, e.g., PBE, LDA, SCAN),
k-point mesh ($\kPointMeshR$), energy cutoff ($\energyCutoffR$), and
pseudopotential type ($\pseudopotentialTypeR$)), and
$\WaveFunctionCalculationC$ (governed by $\WaveFunctionSettingsC$ with the
correlation method ($\wfMethodR$, e.g., CCSD(T), MP2, CASPT2), basis set
($\basisSetR$, e.g., cc-pVTZ), and frozen-core flag ($\frozenCoreR$)).
The supertype $\ReferenceSettingsC$ carries the cross-family software-code
slot ($\usedReferenceCodeR$), of which the DFT-specific $\dlRole{usedDFTCode}$
is a sub-property.
Individual $\AtomicConfigurationC$ instances represent the atomic positions,
cell parameters, and computed properties within a dataset.
\paragraph{Core properties.}
$\hasReferenceCalculationR$ links a dataset to its reference calculation
(with $\hasDFTCalculationR$ as the DFT-specific sub-property);
$\hasReferenceSettingsR$ links a calculation to its settings (with
$\hasDFTSettingsR$ as the sub-property);
$\numConfigurationsR$ records the dataset size;
$\coversPropertyR$ indicates which physical properties
(energy, forces, stresses, virials) are included;
and $\datasetProvenanceR$ classifies the origin
as $\dlConcept{Published}$, $\dlConcept{InHouse}$, or
$\dlConcept{Augmented}$. Augmented datasets are linked to
their sources via PROV-O's \mbox{$\provWasDerivedFromR$}.
The $\samplingStrategyR$ object property
($\TrainingDatasetC \to \SamplingStrategyC$, optional and multi-valued)
records how the configurations were sampled (e.g., chemical sampling
across compositions, vibrational sampling across thermal snapshots, or
a combination). $\SamplingStrategyC$ is left as an open extension
point: concrete strategies are modeled as instances and a controlled
vocabulary will be developed in future work.

\paragraph{Axioms.}
The Training Data module defines 5 existential restrictions: every
$\TrainingDatasetC$ must cover at least one material system, declare at
least one covered property, specify its provenance, and include at least
one atomic configuration; every $\DFTCalculationC$ must have DFT settings.
The provenance classification ($\dlConcept{Published}$,
$\dlConcept{InHouse}$, $\dlConcept{Augmented}$) is exhaustive and disjoint.



\subsection{Benchmark Module}
\label{sec:benchmark-module}

The Benchmark module links published studies to trained models, materials,
and accuracy metrics, addressing CQ6 and CQ7.

\paragraph{Core classes.}
A $\BenchmarkStudyC$ represents a published study reporting MLIP evaluation
results. Each study contains one or more $\BenchmarkResultC$ instances, each
capturing a single evaluation: a $\TrainedModelC$ applied to a material
system. Since a trained model already encodes the algorithm, training data,
and hyperparameter settings (via the Algorithm module), the benchmark result
need only reference the model and the test conditions. Results report
$\AccuracyMetricC$ instances (e.g., RMSE of energy, MAE of forces), each
characterized by a $\MetricTypeC$ (RMSE, MAE, R$^2$), a $\MetricPropertyC$
(energy, force, stress), and a numeric value with unit.

\paragraph{Core properties.}
The role $\evaluatesModelR$ links a benchmark result to the trained model
being evaluated, while $\targetMaterialR$ specifies the material system used
for testing. $\hasAccuracyMetricR$ connects to the reported accuracy values.
Each $\AccuracyMetricC$ is described by $\metricTypeR$, $\metricPropertyR$,
and $\metricValueR$. The role $\reportedInR$ links a result to its source
publication.

\paragraph{Axioms.}
The Benchmark module defines 8 axioms ensuring data completeness: every
$\BenchmarkStudyC$ must contain at least one result; every
$\BenchmarkResultC$ must evaluate exactly one $\TrainedModelC$, target at
least one material system, and report at least one accuracy metric; every
$\AccuracyMetricC$ must specify exactly one metric type and one measured
property. Through the property chains on $\TrainedModelC$, every benchmark
result is transitively linked to the algorithm and training data used,
enabling cross-module queries (CQ6, CQ7) without redundant encoding.



\subsection{Alignment with External Ontologies}
\label{sec:alignment}

The \MLIPsOntology{} reuses established vocabularies wherever an
existing class or property already names the concept at hand:
ML-Schema for the ML workflow, PROV-O for activity-based
provenance, MDO and CMSO for materials science, schema.org for
bibliographic metadata, and QUDT for units. Figure~\ref{fig:alignments}
shows the resulting alignment graph and
Table~\ref{tab:alignment-axioms} catalogues the 22 formal
alignment axioms (L1)--(L22); each arc in the figure carries the
labels of the axioms it represents, and the line width of an arc
encodes the number of axioms collapsed onto it.

The single salient design decision is the disjointness in (L6):
$\MLIPMethodC$ is \emph{not} a subclass of $\mlsAlgorithmC$ but
disjoint from it, because the two classes name different kinds of
thing (a named recipe ``functional form + loss function + training
algorithm'' versus a training procedure such as Adam). The two
vocabularies meet at a single role, $\hasTrainingAlgorithmR$
(L17), which links every MLIP method to its underlying ML-Schema
algorithm. The same disjointness is why $\MLIPRunC$ is a subclass
of $\provActivityC$ only (L3) and not of $\mlsRunC$; an optional
$\hasTrainingRunR$ (L7, L8) reaches an $\mlsRunC$ when the
training procedure is itself modelled in ML-Schema.
Appendix~\ref{sec:appendix-method} discusses this decision in
detail.
